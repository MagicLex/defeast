Feast vs Hopsworks: online serving latency

Same data, same feature model, same query sweep, one machine. Single-thread, warm, SDK path.

Hopsworks retrieves online features 2x to 28x faster at the median, and the gap widens with load. Feast's latency climbs almost linearly with batch size; RonDB stays nearly flat. And Feast had the home advantage: its store (Redis) ran on localhost, Hopsworks went over the network.

How to read this honestly

  • Feast played at home. Its Redis store ran on localhost, zero network. The Hopsworks client went over the network to RonDB with TLS. The advantage was Feast's, and it still lost.
  • This is the median story. At the very smallest query (1 row), Hopsworks shows occasional network tail spikes (~210 ms p99 on some cells) that Feast's localhost avoids. Those are external-client artifacts, not RonDB. Under any real load (batch or many features) Hopsworks wins on every percentile.
  • Same slow path for both. Both numbers are the Python SDK returning a materialized object. This is the default pip install feast path, not the alpha Go feature server Feast benchmarks advertise.
  • Where online serving lives. Recommenders and fraud fetch many entities per request. That is exactly where Feast collapses (253 ms at batch 100) and RonDB holds (9 ms).

300 measured calls per cell after 50 warmup, random entities over a 10k keyspace, 250 int64 features in 25 groups of 10. Run on a 96-core host, 2026-07-27.
