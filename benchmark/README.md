# Online serving latency: Feast vs Hopsworks

Head-to-head on the claim Feast advertises most: low-latency online feature serving. Same data, same feature model, same query sweep, same machine, measured at the same layer.

## Setup

Both sides run on one host (96 cores, 377 GB). Data and feature model are identical, generated by the Feast team's own `data_generator.py` (10k rows, 250 int64 features, entity keyspace 10k).

Feature model mirrors `feast-dev/feast-benchmarks`: 25 groups of 10 features each, retrieved in bundles of 50, 100, 150, 200, 250 features (5, 10, 15, 20, 25 groups joined on `entity`).

- Feast: 25 feature views + 5 feature services, online store Redis 7, `feast materialize-incremental`. `feast_repo/`.
- Hopsworks: 25 feature groups + 5 feature views, online store RonDB. `hops_setup.py`.

## Measurement

`feast_bench.py` and `hops_bench.py` measure the same thing: single-thread, warm, per-call wall time of an online feature retrieval, over a sweep.

- Sweep A: vary batch size (1, 10, 25, 50, 100) at 50 features.
- Sweep B: vary features (50 to 250) at batch size 1.
- Per cell: 50 warmup calls, then 300 measured calls, random entities from the keyspace. Report p50, p90, p99, p99.9, mean, single-thread QPS.

Both clients return a materialized Python object (Feast `get_online_features().to_dict()`, Hopsworks `get_feature_vector(s)`), so the object-construction cost is paid on both sides.

## Fairness notes

- Feast plays at home. Its client hits Redis on `localhost`, zero network. The Hopsworks client goes over the network (host to RonDB via a load-balanced endpoint, with TLS). The advantage is Feast's.
- Same data on both sides, including the entity duplicates and misses the Feast generator produces. A random entity absent from the store returns nulls on both.
- `go_feature_retrieval` is not used. Feast removed it from the core SDK path; this measures the default `pip install feast` Python path, which is what users get.

## Reproduce

```
# data + feast
python data_generator.py                 # from the feast-benchmarks fork
cd feast_repo && feast apply && feast materialize-incremental $(date -u +%FT%T)
python feast_bench.py                     # -> results_feast.jsonl

# hopsworks (needs HOPSWORKS host + api key in ~/.hw_bench_key)
python hops_setup.py                      # 25 FGs + 5 FVs, materialize to RonDB
python hops_bench.py                      # -> results_hops.jsonl
```

Results land as JSONL, one object per cell. `report.html` is the rendered comparison (source of the shared artifact).

## Security note

The Redis online store must bind to `127.0.0.1` only, never `0.0.0.0`. The benchmark host is shared and internet-facing. An early run bound Redis on `0.0.0.0:6379` and within minutes an automated scanner hit it and injected Redis cron-injection payloads (the classic `SET` a crontab entry, `CONFIG SET dir`, `SAVE` attack pointing at a remote miner dropper). It was fully contained by rootless podman: the container Redis runs as an unprivileged user with `dir=/data` inside its own mount namespace, so it could not reach the host crontab, and the host was verified clean (no user crontab, no matching entries in `/etc/cron.d` or `/var/spool/cron`, no outbound connections, no miner process). The store now runs on `127.0.0.1:6771` with `--bind 127.0.0.1 --save '' --appendonly no`. The first Feast SDK run overlapped this window and was re-run on the clean, isolated store.
